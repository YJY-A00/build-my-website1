# 网站部署故障排查记录

本文整理第一次建站实践总结中出现的问题。每个案例均应标注发生阶段，并尽量保留脱敏后的错误日志、定位过程和验证结果。

> 目前以下案例来自第一次实践后的总结。除非后续确认在第二次部署中也出现，否则不要将其写成第二次部署故障。

## 记录模板

每次新增问题建议按以下格式记录：

- **发生阶段：** 第一次部署 / 第二次部署
- **问题现象：** 用户看到什么，或命令输出什么
- **环境信息：** 操作系统、软件版本、执行位置
- **错误信息：** 脱敏后的完整报错或关键日志
- **排查过程：** 检查了什么，排除了什么
- **原因分析：** 有证据支持的原因
- **解决办法：** 实际执行的修改
- **验证结果：** 如何确认问题解决
- **经验总结：** 如何避免再次发生

## 1. 云服务器防火墙未放行端口

- **发生阶段：** 第一次部署总结。
- **问题现象：** Nginx 安装成功，但外网无法访问网站。
- **原总结中的处理：** 在云平台安全组中放行 TCP 22（SSH）、80（HTTP）、443（HTTPS）端口。
- **需要理解：** 云平台安全组和服务器内部防火墙是不同层面的访问控制；应分别检查，不能只看其中一处。
- **验证方式：** 从外部网络测试网站端口，并检查 Nginx 服务状态。

## 2. Go 依赖下载超时

- **发生阶段：** 第一次部署总结。
- **问题现象：** 执行 `go get` 拉取依赖时出现网络超时，例如 `dial tcp ... i/o timeout`。
- **原总结中的处理：** 配置 Go 模块代理，例如 `go env -w GOPROXY=https://goproxy.cn,direct`。
- **验证方式：** 重新执行依赖下载命令，并确认依赖能够正常解析和下载。
- **注意：** 代理地址应根据当前网络环境和可用性选择。

## 3. Vim 编辑器使用困难

- **发生阶段：** 第一次部署总结。
- **问题现象：** 在终端使用 Vim 粘贴代码时格式混乱，新手不熟悉编辑和退出操作。
- **原总结中的处理：** 使用 Shell here-document 写入文件，例如：

```bash
cat > 文件名 <<'EOF'
在这里放入文件内容
EOF
```

- **注意：** 覆盖写入前确认目标路径和原文件是否需要备份。

## 4. MySQL 密码特殊字符导致连接配置问题

- **发生阶段：** 第一次部署总结。
- **问题现象：** 原总结记录数据库密码包含 `@`，Go 数据库连接字符串解析失败。
- **原总结中的处理：** 当时将密码改为字母和数字组合，并执行权限刷新。
- **补充说明：** 不应为了绕过 DSN 问题而把密码改成弱口令。go-sql-driver/mysql 文档说明密码可以包含任意字符；应检查 DSN 生成方式、Shell 引号、环境变量读取和连接参数，不要把密码硬编码到源码或公开仓库。
- **验证方式：** 使用脱敏配置确认 Go 服务可以连接数据库。

## 5. Systemd 服务启动失败（status=203/EXEC）

- **发生阶段：** 第一次部署总结。
- **问题现象：** 配置了 `myapp.service`，但启动时报错 `status=203/EXEC`。
- **原总结中的原因：** Go 程序未成功编译，导致服务配置指向的可执行文件不存在。
- **原总结中的处理：** 重新执行构建，例如 `go build -o myapp .`，并检查目标文件是否存在及是否具有执行权限。
- **验证方式：** 检查服务状态和日志，确认服务实际启动并监听预期地址。

## 6. Linux 与 Windows 终端混用

- **发生阶段：** 第一次部署总结。
- **问题现象：** 在本地 Windows PowerShell 中执行 Linux 的 `chown` 等命令导致报错。
- **原总结中的处理：** 区分本地和服务器环境：本地使用 SSH 连接及 SCP 传输文件；服务器端执行 Linux 管理命令。
- **经验：** 执行命令前先确认当前终端、主机和工作目录。

## 7. Nginx 动静态分离配置

- **发生阶段：** 第一次部署总结。
- **处理思路：** 使用 `location /` 处理前端静态资源，使用 `location /api/` 配合 `proxy_pass` 将 API 请求转发给内部 Go 服务。
- **验证方式：** 分别访问首页静态资源和 API 路径，并检查 Nginx 与 Go 服务日志。
- **注意：** `location` 匹配和 `proxy_pass` 尾部斜杠会影响 URI 转发结果，实际配置应结合接口路径验证。

## 8. 前端页面中文乱码

- **发生阶段：** 第一次部署总结。
- **原总结中的处理：** 在 HTML 中声明 UTF-8，例如：

```html
<meta charset="UTF-8">
```

- **还应检查：** 源文件实际编码、HTTP 响应头字符集，以及数据源编码是否一致。
- **验证方式：** 检查页面源文件和浏览器响应，确认中文显示正常。

## 9. 文件名不规范导致 404

- **发生阶段：** 第一次部署总结。
- **问题现象：** 新代码上传后页面没有变化，原总结记录文件名为 `index (2).html`，而 Nginx 默认首页配置查找 `index.html`。
- **原总结中的处理：** 将文件重命名为预期名称，并确认 Nginx 的 root 和 index 配置。
- **验证方式：** 检查服务器目录中的实际文件名，并请求对应 URL。

## 10. 浏览器缓存导致页面看起来没有更新

- **发生阶段：** 第一次部署总结。
- **原总结中的处理：** 强制刷新浏览器，或使用无痕窗口进行对照测试。
- **进一步排查：** 检查静态资源缓存响应头、文件是否部署到正确目录，以及 CDN 或代理缓存（如有）。

## 11. 域名注册与使用条件

- **发生阶段：** 第一次部署总结。
- **原总结涉及：** 域名注册商、域名后缀和在境内提供网站服务时涉及的备案要求。
- **注意：** 域名注册商、注册地、服务器接入地和网站服务内容会影响具体合规要求。涉及备案的判断应以主管部门和接入服务商的最新要求为准，不应仅凭后缀判断。

## 12. ICP 备案流程

- **发生阶段：** 第一次部署总结。
- **原总结记录的流程：** 域名购买、实名认证、等待注册信息同步、提交服务商初审、主管部门审核。
- **注意：** 具体步骤、审核时长和材料要求可能变化，应以实际办理平台显示为准。
- **隐私提醒：** 不要在公开仓库中上传身份证件、手机号、个人住址、备案后台截图等敏感资料。

## 13. HTTPS 证书申请与续期

- **发生阶段：** 第一次部署总结。
- **原总结中的工具：** Certbot 与 Let's Encrypt。
- **原总结中的处理：** 使用 Certbot 申请证书，并配置 Nginx 的 HTTPS 访问和证书续期。
- **验证方式：** 检查证书有效期、HTTPS 访问和自动续期任务；可使用 Certbot 提供的续期测试命令验证。
- **注意：** 不要假设证书一定会自动续期，需实际检查定时任务和续期测试结果。

## 第二次部署排查清单（诊断建议，非已发生故障记录）

以下项目根据第二次部署所用的 Go、MySQL、Systemd 和 Nginx 配置整理，用于实际出现故障时逐项检查。当前没有证据证明这些问题已经在第二次部署中发生，因此不将它们记作已发生故障。

### 1. Go 服务启动失败或 Systemd 报 203/EXEC

先核对可执行文件路径、权限、CPU 架构和服务配置：

```bash
ls -l /opt/myapp/myapp
file /opt/myapp/myapp
sudo systemd-analyze verify /etc/systemd/system/myapp.service
sudo journalctl -u myapp -n 100 --no-pager
```

常见原因包括：`ExecStart` 路径写错、文件不存在、没有执行权限、二进制架构不匹配，或服务用户无法遍历上级目录。修正后执行 `sudo systemctl daemon-reload`，再重启服务并检查日志。

### 2. Nginx 返回 502 Bad Gateway

先确认 Go 服务是否监听在 Nginx 配置的地址和端口：

```bash
sudo systemctl status myapp
sudo ss -lntp | grep 8080
curl -i http://127.0.0.1:8080/实际健康检查路径
sudo tail -n 100 /var/log/nginx/error.log
```

重点核对 Go 实际监听地址、端口与 `proxy_pass` 是否一致。若 Go 只监听 `127.0.0.1:8080`，从外部网络无法直接访问 8080 是预期行为，应该通过 Nginx 访问。

### 3. Go 连接 MySQL 失败

检查数据库服务、应用账户和连接方式：

```bash
sudo systemctl status mysql
sudo ss -lntp | grep 3306
mysql --version
```

若错误为 `Access denied`，核对用户名、密码、数据库名，以及 MySQL 账户的 Host 部分。特别注意：`'myapp'@'localhost'` 与通过 TCP 连接 `127.0.0.1:3306` 的账户匹配可能不同；应让账户 Host 与 Go DSN 的实际连接协议/地址一致。不要为解决本机连接问题而把 3306 暴露到公网。

若错误为连接拒绝，检查 MySQL 是否运行、监听地址是否正确，以及 Go 程序是否在数据库启动后进行重试。日志和配置输出中应对密码脱敏。

### 4. API 路径 404 或请求落入前端页面

检查 Nginx 的 `location /api/` 是否被正确加载，并核对 `proxy_pass` 是否保留或剥离 `/api/` 前缀。当前示例的 `proxy_pass http://127.0.0.1:8080;` 会将原 URI 转发给后端；如果 Go 路由不包含 `/api` 前缀，应按 Nginx URI 替换规则调整配置。修改后执行：

```bash
sudo nginx -t
sudo systemctl reload nginx
```

同时分别用本机 curl 直连 Go 接口和通过 Nginx 访问同一接口，定位问题发生在哪一层。

### 5. 域名无法访问或 Certbot 申请失败

依次检查域名 A/AAAA 记录、服务器公网 IP、云安全组、UFW、Nginx 监听和域名对应的 `server_name`。HTTP-01 验证通常需要验证方能从公网访问域名的 TCP 80 端口；若 80 端口未开放、DNS 指向错误或请求被其他站点配置接管，证书申请可能失败。

```bash
sudo ufw status verbose
sudo ss -lntp | grep -E ':80|:443'
sudo nginx -t
sudo certbot certificates
sudo certbot renew --dry-run
```

不要仅凭 Certbot 命令执行过就声称证书签发成功；应检查证书列表，并实际通过 HTTPS 请求验证域名和证书。

### 6. 防火墙启用后 SSH 连接不上

先通过云厂商 VNC/管理终端恢复访问，再检查 SSH 实际监听端口、UFW 规则和云安全组。不要默认 SSH 一定使用 22 端口。后续启用 UFW 前，先添加正确的 SSH 允许规则并用 `sudo ufw show added` 检查。
